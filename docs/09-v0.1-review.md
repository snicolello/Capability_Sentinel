# v0.1 review and acceptance

## Decision

ARRM v0.1 is **accepted** as a deterministic offline assessor of declared policy against a valid, ordered, trusted trace. This acceptance is limited to the claim in [the problem statement](00-problem-statement.md): for each supplied event, ARRM reports whether a rule with the same capability and matching typed target exists. It is not acceptance of collection completeness, runtime mediation, enforcement, effective-authority analysis, or containment.

M5 stops here. M6 runtime-integration discovery remains unstarted and requires a separate design decision and authorization.

## Definition of done

The implementation plan referred to ten definition-of-done statements without enumerating them. The approved problem statement contains five claimable security properties and six invariants; its fail-closed invariant repeats the third security property. M5 reconciles those eleven bullets into the following ten unique obligations.

| # | Obligation | Evidence | Result |
|---:|---|---|---|
| 1 | Every well-formed event is evaluated exactly once in trace order. | `tests/unit/evaluate-run.test.js`; scenario ordering and byte checks in `tests/contract/full-scenarios.test.js`; the single ordered loop in `src/evaluate/evaluate-run.js` | Pass |
| 2 | `ALLOW` requires a rule with the same capability and a matching typed target. | All six declarable matchers in `tests/unit/match-target.test.js`; CLI coverage for the later matchers in `tests/integration/assess-cli.test.js` | Pass |
| 3 | An absent rule, `UNCLASSIFIED`, malformed input, unknown input, or unexpected evaluator state cannot silently become `ALLOW`. This includes the duplicate fail-closed invariant. | `tests/unit/evaluate-run.test.js`, `tests/unit/schema-validation.test.js`, invalid-input CLI tests, and mandatory failures in `tests/contract/full-scenarios.test.js` | Pass |
| 4 | Identical inputs produce the same ordered assessment. | `tests/unit/stable-json.test.js`; every scenario runs twice and matches `fixtures/expected/*.assessment.json` byte for byte | Pass |
| 5 | Every finding identifies its event, reason, severity, and prescribed response. | `schemas/finding.schema.json`; scenario/finding schema validation and scenario E assertions in `tests/contract/full-scenarios.test.js`; text tests | Pass |
| 6 | An unmatched event is drift; an empty valid trace is only vacuously `ALLOW`. | Unmatched-capability matrix in `tests/unit/evaluate-run.test.js`; empty and `UNCLASSIFIED` cases in `tests/contract/full-scenarios.test.js` | Pass |
| 7 | The core consumes structured events and does not infer security meaning from arbitrary shell command strings. | Typed-target schema contracts; exact process tuple tests; the normalization boundary in `03-event-model.md` | Pass; a deliberate input-model limitation |
| 8 | Core decisions do not depend on network access, live target resolution, an LLM, wall-clock time, randomness, environment interpolation, or locale ordering. | M5 production-import and dependency inventory; evaluator/normalizer source review; lexical path tests | Pass; source/surface invariant rather than a black-box proof |
| 9 | `BLOCK` and `TERMINATE` are prescribed decisions, not claims that enforcement occurred. | `tests/unit/text.test.js`; CLI text parity tests; `src/render/text.js` | Pass |

The human-readable finding output now states that `NO_MATCHING_ALLOW_RULE` means “no allow rule matched this observed operation.” Canonical JSON retains the stable machine reason code.

## Dependency and trusted-surface review

The only direct production dependencies remain exactly pinned:

- `ajv@8.20.0` for strict Draft 2020-12 validation;
- `ajv-formats@3.0.1` for bounded `date-time` validation; and
- `jsonc-parser@3.3.1` for strict parsing with duplicate-key detection.

The transitive packages are Ajv's `fast-deep-equal`, `fast-uri`, `json-schema-traverse`, and `require-from-string`. There are no development dependency families, install scripts, CLI framework, logger, HTTP client, YAML parser, database, general policy engine, or LLM package. The advisory result is point-in-time evidence, not a promise about future advisories.

Application-directed filesystem input is confined to `src/io/load-json.js`. The CLI orchestrates two bounded file reads and writes the result or a diagnostic to the supplied process streams. Repository-owned schemas are static module imports. Production code does not spawn processes or import networking, DNS, or runtime collection facilities. The implemented “audit writer” is stdout emission; there is no persistent audit store or output-file option.

Policy files are limited to 1 MiB and trace files to 64 MiB. Schemas additionally cap rules, events, identifiers, paths, arguments, and timestamps. Syntax diagnostics contain a stable code and location but not source content. Schema details are not printed by the CLI. Valid output intentionally contains typed target metadata—including paths, process arguments, hosts, tool names, and credential identifiers—so consumers must protect assessment output even though credential values are structurally forbidden.

## Residual limitations

- The collector, trace attribution, policy author, policy file, evaluator, and output channel remain trusted. No signature, provenance, or tamper-evident storage exists.
- Input mutation detection compares file size and modification time around a single-handle read. It catches ordinary concurrent changes, not adversarial same-size/same-time replacement or hostile filesystem behavior.
- File and schema bounds reduce accidental resource exhaustion but do not create a CPU or memory guarantee. Evaluation is proportional to events times rules, and a large schema-valid trace can amplify memory through parsing, validation, assessment construction, and serialization.
- Lexical path matching does not establish filesystem object identity. Network origin matching does not establish the ultimate peer. Direct process and named-tool matching does not cover descendants or tool-internal effects.
- Assessment output is an audit record, not a redacted telemetry view. Target names may themselves be sensitive.

None of these residuals contradicts the accepted offline, trusted-input v0.1 claim. Each would become a design requirement before a stronger runtime claim.

## Lessons learned

1. A narrow claim made the evaluator total and testable; separating observed operations from effective authority prevented a small monitor from becoming an unreviewable platform.
2. Canonical typed targets remove ambiguity, but they transfer normalization and attribution obligations to a future collector. Those obligations must be measured at a real execution boundary before integration.
3. Deterministic fixtures are effective audit evidence: byte equality, schema validation, and explicit precedence exposed behavior more clearly than implementation descriptions alone.
4. Fail-closed handling needs separate tests for malformed input, valid-but-unclassifiable input, and unexpected internal state. They are different failure domains and must not share an `ALLOW` path.
5. Human-readable security language matters independently of machine codes. A stable reason enum did not by itself satisfy the requirement to explain what drift means.
6. Small dependency count does not eliminate supply-chain or availability risk; point-in-time audit results and bounded files must remain qualified evidence.
7. Milestone documents can become security-relevant when they define claim boundaries. The stale README and the ambiguous “ten statements” reference were corrected as part of the stop gate rather than carried forward.

## Formal stop gate

**Accepted:** ARRM v0.1 directly compares declared rules with operations in a supplied canonical trace and deterministically emits auditable prescribed decisions.

**Not accepted or implemented:** runtime collection, mediation, enforcement outcomes, path or peer identity, process-tree coverage, effective-capability composition, persistence, dashboards, YAML, AEF integration, or any other M6/deferred subsystem.

Any continuation beyond this point must begin with a separately authorized M6 design gate. It must not treat this v0.1 acceptance as evidence of containment or complete runtime visibility.
